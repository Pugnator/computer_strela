# Simulated time and source distinction

The [Ershov-Shura-Bura historical table](https://ershov.iis.nsk.su/ru/foundation/index) gives Strela a **220 microseconds main tact** and an average **2,000 operations/s**. The [Russian Virtual Computer Museum profile](https://www.computer-museum.ru/english/strela.htm) instead says "clock time 500 mks" and also gives 2,000 three-address commands/s and a 20 microseconds RAM access cycle. Those labels conflict if read as the same hardware interval. The 500 microseconds figure is arithmetically the mean operation interval at 2,000/s; treating it as a distinct instruction interval is an *inference*, not a demonstrated mapping of 220 microseconds tacts to each opcode.

The emulator records `main_tact_us = 220` as a sourced machine parameter. Its default nominal instruction interval is `instruction_us = 500`, explicitly marked **throughput-derived estimate**. `strela_t.cycles` remains a compatibility count of nominal instruction equivalents. `strela_t.elapsed_us` is the independent monotonic simulated clock and is what the CLI reports. The opaque API accepts both timing fields; a caller can compare profiles. The engine does not yet reconstruct the hardware's microtact sequence, so it must not claim that one opcode always uses one 220 microseconds tact.

Normal one-word instructions currently cost one nominal interval. A group prefix costs one interval, followed by one per repetition. Standard-function batches commit and charge each result separately, so a time budget may overshoot by at most one element. RAM copy and card/tape transfers commit one word per nominal interval. Card and tape operations also pay the configured start delay once and the configured per-word delay at each word boundary; these are estimates. [Carr's report on Soviet computers, reprinted by Bell and Newell](https://gordonbell.azurewebsites.net/Computer_Structures__Readings_and_Examples/00000234.htm) gives approximate standard-subprogram costs: reciprocal 18-20, square root 40, exponential 40, logarithm 60, and sine 25. We use 20, 40, 40, 60, and 25 nominal intervals per element. BCD conversion (70 and 72) uses 50 and arctangent/arcsine 40; these four values are our estimates, not from Carr. RAM-to-RAM copy (45) charges one nominal interval per word and no device delay.

No primary transport timing has been located for card or tape. The default start, movement, and per-word delays below form an explicit engineering estimate profile. The [Polytechnic Museum's](https://polymus.ru/collection/detail/bloki-elektronnoy-vychislitelnoy-mashiny-strela) 100-million-operation / 17-hour workload implies about 1,634 operations/s across a real job; it is a plausibility check, not an opcode timing table.

## Current estimated device profile

The default profile currently uses card start 10,000 us, card word 1,000 us, tape start 20,000 us, tape word 500 us, and tape supply movement 50,000 us. These are **engineering placeholders**, not measurements from either historical source. They are public timing-profile fields and can be set to zero for comparisons. An opcode 25 supply schedules a completion event at the current simulated time plus one nominal instruction interval plus the movement delay. Independent CPU instructions can run while it is pending. A later tape operation waits until that event completes. A run-for-time budget may overshoot by one completed standard-function or block-transfer element. Equal-time events are delivered in issue order.
